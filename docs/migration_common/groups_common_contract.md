# Contrat de migration des groupes vers `common`

## Objectif

Ce document fige le contrat cible pour déplacer les tables de groupes du
schéma `lss` vers le schéma partagé `common`.

Les groupes deviennent une ressource commune entre `Lyrics Slide Show` (`LSS`)
et `Animation-messe` (`AM`). LSS conserve un CRUD complet sur les groupes, les
membres et les demandes d'adhésion, mais les données ne sont plus propres au
schéma `lss`.

Ce contrat sert de source de vérité pour les étapes suivantes :

- création SQL des tables `common` par un niveau supérieur ;
- migration des données par `INSERT SELECT` ;
- ajout des contraintes, index, clés étrangères et triggers ;
- adaptation du code Django LSS ;
- renommage temporaire des anciennes tables `lss` ;
- suppression finale des anciennes tables après validation.

## Règles fonctionnelles partagées

L'appartenance à un groupe est unique et commune.

Une ligne dans `common.g_group_user` signifie que le membre appartient au groupe
pour LSS et pour AM.

Pour LSS, l'appartenance au groupe suffit. LSS ignore le champ `am_access`.

Pour AM, l'appartenance commune ne suffit pas toujours. AM exige en plus
`am_access = true` pour autoriser l'usage d'AM dans ce groupe.

Les rôles avancés propres à AM restent hors du schéma `common` et sont gérés
dans le schéma AM.

Les rôles globaux propres à LSS restent hors du schéma `common` et sont gérés
dans `lss.m_member_roles`.

Le champ `is_group_admin` reste commun, car la gouvernance simple du groupe est
commune aux applications.

## DDL cible

Les tables attendues dans le schéma `common` sont les suivantes.

```sql
CREATE TABLE common.g_groups (
  group_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name varchar(255) NOT NULL,
  info text NULL,
  secret_ciphertext text NULL,
  status varchar(32) NOT NULL DEFAULT 'open',
  CONSTRAINT g_groups_status_check
    CHECK (status IN ('open', 'private'))
);

CREATE UNIQUE INDEX g_groups_name_unique
  ON common.g_groups (lower(name));

CREATE INDEX g_groups_status_idx
  ON common.g_groups (status);

CREATE TABLE common.g_group_user (
  group_id integer NOT NULL,
  member_id uuid NOT NULL,
  is_group_admin boolean NOT NULL DEFAULT false,
  am_access boolean NOT NULL DEFAULT false,
  PRIMARY KEY (group_id, member_id),
  CONSTRAINT g_group_user_group_fk
    FOREIGN KEY (group_id)
    REFERENCES common.g_groups (group_id)
    ON DELETE CASCADE,
  CONSTRAINT g_group_user_member_fk
    FOREIGN KEY (member_id)
    REFERENCES users.users (id)
    ON DELETE CASCADE
);

CREATE INDEX g_group_user_is_group_admin_idx
  ON common.g_group_user (is_group_admin);

CREATE INDEX g_group_user_am_access_idx
  ON common.g_group_user (am_access);

CREATE TABLE common.g_group_user_ask_to_join (
  group_id integer NOT NULL,
  member_id uuid NOT NULL,
  PRIMARY KEY (group_id, member_id),
  CONSTRAINT g_group_user_ask_to_join_group_fk
    FOREIGN KEY (group_id)
    REFERENCES common.g_groups (group_id)
    ON DELETE CASCADE,
  CONSTRAINT g_group_user_ask_to_join_member_fk
    FOREIGN KEY (member_id)
    REFERENCES users.users (id)
    ON DELETE CASCADE
);
```

## Trigger attendu

La base cible doit prévoir un trigger de nettoyage des demandes d'adhésion.

Comportement attendu :

- le trigger se déclenche après suppression d'une ligne dans
  `common.g_group_user` ;
- il supprime automatiquement la ligne résiduelle équivalente dans
  `common.g_group_user_ask_to_join` ;
- la fonction et le trigger sont placés dans le schéma `common`.

Exemple de forme attendue :

```sql
CREATE OR REPLACE FUNCTION common.delete_group_join_request_on_membership_delete()
RETURNS TRIGGER AS $$
BEGIN
  DELETE FROM common.g_group_user_ask_to_join
  WHERE group_id = OLD.group_id AND member_id = OLD.member_id;
  RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER g_group_user_delete_join_request_cleanup
AFTER DELETE ON common.g_group_user
FOR EACH ROW
EXECUTE FUNCTION common.delete_group_join_request_on_membership_delete();
```

## Contraintes de migration

Les `group_id` existants doivent être conservés. Aucune remappe d'identifiants
ne doit être nécessaire pour LSS.

Les tables `common` sont créées par un script SQL géré à un niveau supérieur.
Elles ne sont pas créées par les migrations Django LSS.

Après la migration des données par `INSERT SELECT`, l'identity de
`common.g_groups.group_id` doit être recalée sur le `MAX(group_id)` migré.

La clé étrangère `lss.a_animations.group_id` devra pointer vers
`common.g_groups(group_id)` dans une étape ultérieure.

Les anciennes tables suivantes ne sont pas supprimées à l'étape 1 :

- `lss.g_groups` ;
- `lss.g_group_user` ;
- `lss.g_group_user_ask_to_join`.

Elles seront renommées dans une étape ultérieure afin de détecter tout appel
accidentel résiduel vers l'ancien schéma, puis supprimées seulement après
validation.

## Validation de l'étape 1

L'étape 1 est complète lorsque :

- le document `docs/migration_common/groups_common_contract.md` existe ;
- le contrat mentionne explicitement `am_access` ;
- le contrat dit clairement que LSS ignore `am_access` ;
- le contrat dit clairement que les tables `common` sont provisionnées hors
  migrations Django LSS ;
- le DDL référence `users.users(id)` ;
- le DDL conserve les clés primaires `(group_id, member_id)` pour
  `common.g_group_user` et `common.g_group_user_ask_to_join`.

## Hypothèses figées

- Le booléen AM s'appelle `am_access`.
- `am_access = false` par défaut.
- `is_group_admin` reste commun.
- Les rôles spécifiques AM restent dans le schéma AM.
- Les rôles globaux LSS restent dans `lss.m_member_roles`.
